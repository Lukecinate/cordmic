# Releasing CordMic

This is the whole release chain for 0.8.0 and later. Version numbers, tags, and
GitHub releases are created by the maintainer. Automated jobs must not push
tags or publish a latest release on their own without the verify-and-publish
dispatch after a human review.

**Deputy (SignPath approver backup and K2 holder): _not yet named_.**

## Roles and keys

- **K1** (primary offline ECDSA P-256 key) and **K2** (backup) are generated by
  the maintainer with `tools/keytool` (`cordmic-keytool generate`). Private keys
  stay on two USB sticks each, passphrases on paper in a separate place. Only
  the public keys and key IDs are sent for embedding in `ReleaseKeys.cs` and
  `ReleaseKeys.kt`.
- **SignPath** signs Windows PE files and the installer after manual approval.
- **Android keystore:** the existing upload key, backed up per `docs/KEYSTORE-BACKUP.md`.
- Yearly reminder: plug in both sticks for K1 and both for K2 and run
  `cordmic-keytool check` on each copy.

## Chain (every non-key step is scripted)

1. **Tests** — `test-windows` and `test-android` in `.github/workflows/release.yml`.
2. **Unsigned build** — deterministic `dotnet publish` (`ContinuousIntegrationBuild=true`,
   `Deterministic=true`, `SourceRevisionId`) and an unsigned Android `assembleRelease`
   (no keystore on the runner).
3. **Sign inner binaries** — SignPath `inner-binaries` and `driver-catalog`, manual
   approval. The API token lives in the `release` environment. Jobs never use `set -x`.
4. **Package** — NSIS installer and portable zip from the signed binaries.
5. **Sign installer** — SignPath `installer`.
6. **Provenance** — `actions/attest-build-provenance` and a CycloneDX SBOM.
7. **Draft release** — `SHA256SUMS`, unsigned `release-manifest.json`, a GitHub
   *draft* (not latest, not published).
8. **APK signing (maintainer, scripted, key stays private)** —
   `tools/release/sign-apk.sh` on a private machine. Upload the signed APK to the draft.
9. **Manifest signing (manual, by design)** — on an offline-capable machine:
   `cordmic-keytool sign release-manifest.json --key E:\cordmic-release-K1.p8`.
   Check the printed version, names, sizes and hashes, then upload
   `release-manifest.json.sig`. Unplug the stick.
10. **Verify and publish** — `workflow_dispatch` only, environment `release`.
    `tools/release/publish-checks.sh` checks Authenticode, the manifest signature
    (once production keys are embedded), every hash, `gh attestation verify`,
    the APK certificate SHA-256, and Gate H (`tools/release/verify-gate-h.sh`).
    Only then is the release published as latest (or as a pre-release if the tag
    contains `-beta` / `-rc`).

Until K1/K2 public keys are embedded, step 10 still requires SHA-256SUMS and
the other checks, but it cannot require a production manifest signature. The
updater likewise keeps the SHA-256SUMS path until those keys are present.

## Tag and version rules

- Release tags look like `v0.8.0` or `v0.8.0-beta.2`. Never move a tag.
- A pre-release must be published with `prerelease: true` so the in-app updater
  (which ignores pre-releases) does not move 0.7.2 users onto a beta.
- 0.7.2 stays the current stable release until 0.8.0 is published as latest.
